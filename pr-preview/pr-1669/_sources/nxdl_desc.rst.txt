attributeType
-------------



Any new NeXus group or field may expect or require some common NeXus attributes.

..

XML attributes of attributeType
+++++++++++++++++++++++++++++++

XML attribute name
++++++++++++++++++

    

    Name of the NeXus attribute (unique among the NeXus attributes of its NeXus group or field).

    or *required* (if **false**)?

.. _NXDL.data.type.definitionType:

definitionType
--------------



A ``definition`` is the root element of every NXDL definition.
It may *only* appear at the root of an NXDL file and must only 
appear **once** for the NXDL to be *well-formed*.

The ``definitionType`` declares the XML attributes of the NXDL definition
and the NXDL docs, attributes, fields and groups
that will be used as its children.
Could contain these elements:

* ``attribute``
* ``doc``
* ``field``
* ``fieldAttributes``
* ``group``
* ``link``

Note that an NXDL definition also includes the declarations of the 
``basicComponent`` complex type.
(The ``definitionType`` complex type is used internally in the NXDL schema 
to declare elements and XML attributes to be used in NXDL files.)

Note that the first line of text in an NXDL doc in an NXDL definition
is used as a summary in the manual.  Follow the pattern as shown
in the base class NXDL files.


XML attributes of definitionType
++++++++++++++++++++++++++++++++

XML attribute category
++++++++++++++++++++++

    

    NXDL ``base`` definitions define the NeXus items
    to use for these components.
    All NeXus items of a base class are optional, except the
    NeXus attribute ``@NX_class`` of a NeXus group (see :ref:`NXobject`).
    NXDL ``application`` definitions define what is
    required for a scientific interest.
    All NeXus items of an application definition
    are required, unless their XML attributes say otherwise.
    NXDL ``contributed`` definitions may be
    considered either base or applications.
    Contributed definitions must indicate
    their intended use, either as a base class or
    as an application definition.
    

XML attribute extends
+++++++++++++++++++++

    

    The XML attribute ``extends`` allows this definition
    to *subclass* from another NXDL,
    otherwise ``extends="NXobject"`` should be used.
    

XML attribute ignoreExtraAttributes
+++++++++++++++++++++++++++++++++++

    

    Only validate known content attributes; do not not warn about unknowns.
    The XML attribute ``ignoreExtraAttributes`` is a flag to the process of
    validating NeXus data files.  By setting ``ignoreExtraAttributes="true"``,
    presence of any content attributes that no NeXus attribute describes, in a content group of this class, will not generate warnings
    during validation.  Normally, validation will check all the content attributes
    against the NeXus items of the base classes and
    application definitions that describe them.  Any content that no
    NeXus item describes will generate a warning message.
    
    The XML attribute ``ignoreExtraAttributes`` should be used sparingly!
    

XML attribute ignoreExtraFields
+++++++++++++++++++++++++++++++

    

    Only validate known content fields; do not not warn about unknowns.
    The XML attribute ``ignoreExtraFields`` is a flag to the process of
    validating NeXus data files.  By setting ``ignoreExtraFields="true"``,
    presence of any content fields that no NeXus field describes, in a content group of this class, will not generate warnings
    during validation.  Normally, validation will check all the content fields against
    the NeXus items of the base classes and
    application definitions that describe them.  Any content that no
    NeXus item describes will generate a warning message.
    
    The XML attribute ``ignoreExtraFields`` should be used sparingly!
    

XML attribute ignoreExtraGroups
+++++++++++++++++++++++++++++++

    

    Only validate known content groups; do not not warn about unknowns.
    The XML attribute ``ignoreExtraGroups`` is a flag to the process of
    validating NeXus data files.  By setting ``ignoreExtraGroups="true"``,
    presence of any content groups that no NeXus group describes, in a content group of this class, will not generate warnings
    during validation.  Normally, validation will check all the content groups against
    the NeXus items of the base classes and
    application definitions that describe them.  Any content that no
    NeXus item describes will generate a warning message.
    
    The XML attribute ``ignoreExtraGroups`` should be used sparingly!
    

XML attribute name
++++++++++++++++++

    

    The ``name`` of this NXDL file (case sensitive without the file extension).
    The name must be unique amongst all the NeXus base class, application,
    and contributed definitions.  For the class to be adopted by the NIAC,
    the first two letters must be "``NX``" (in uppercase).  Any other use
    must *not* begin with "``NX``" in any combination
    of upper or lower case.
    

XML attribute restricts
+++++++++++++++++++++++

    

    The XML attribute ``restricts`` is a flag to the data validation.
    When ``restricts="1"``, any non-standard component found
    (and checked for validity against this NXDL specification)
    in a NeXus data file will be flagged as an error.  If the
    XML attribute ``restricts`` is not present, any such situations
    will produce a warning.
    

XML attribute svnid
+++++++++++++++++++

    

    (2014-08-19: deprecated since switch to GitHub version control)
    The identifier string from the subversion revision control system.
    This reports the time stamp and the revision number of this file.
    

XML attribute type
++++++++++++++++++

    

    Must be ``type="group"``
    

Elements of definitionType
++++++++++++++++++++++++++

fieldAttributes
+++++++++++++++

    

    Defines NeXus attributes that describe the content attributes of
    every content field directly in a content group of this class.
    Like the other NeXus items of a class, they are inherited
    by the classes that extend it.
    

symbols
+++++++

    

    Use a ``symbols`` list  
    to define each of the mnemonics that
    represent the length of each dimension in a vector or array.
    

Model groups of definitionType
++++++++++++++++++++++++++++++

    

    In addition to an optional ``symbols`` list,
    an NXDL definition may contain any of the elements
    allowed in an NXDL group.

.. _NXDL.data.type.enumerationType:

enumerationType
---------------



An NXDL enumeration restricts the values allowed for a NeXus field or attribute.
Each value is specified using an ``item`` element, such as:
``<item value="Synchrotron X-ray Source" />``.
Could contain these elements:

* ``doc``
* ``item``

(This complex type is used internally in the NXDL schema 
to declare elements and XML attributes to be used in NXDL files.)

::


		source operating mode

			for storage rings
			for storage rings




Enumerations can be closed or open. A closed enumeration is one where the list of
values are the only ones allowed for a specification. An open enumeration is one 
where the list of values is incomplete and additional values other than those listed
are allowed. Open enumerations should be used sparingly as the designer of the enumeration
should try to find all possible values for a given NeXus field or attribute.

In case an open enumeration is used and the data provider wants to declare that the provided
value deliberately not from the given list of values, the data provider should,

* for content fields, set the content attribute ``@custom=True``.
* for content attributes, set an additional content attribute ``@my_attribute_custom=True``, where
  ``my_attribute`` is the name of the content attribute with the open enumeration.

Such content attributes can be used deliberately to suppress warnings in NeXus validators.

+++++++++++++++++++++++++++++++++

XML attribute open
++++++++++++++++++

    An open enumeration allows additional values not listed.

.. _NXDL.data.type.fieldType:

fieldType
---------



An NXDL field defines a NeXus field of the class or NeXus group being defined.
That NeXus field describes content fields, which are stored as an HDF4 SDS
(Scientific Data Set) or an HDF5 *dataset*.   Could contain these elements:

* ``attribute``
* ``dimensions``
* ``doc``
* ``enumeration``

The XML attributes ``long_name``, ``signal``, ``axes``, ``axis``,
``primary``, ``interpretation``, ``stride`` and ``data_offset``
of an NXDL field give the value of the content attribute
with that name of the content fields that the NeXus field describes, for
example ``signal="1"``; their declarations below constrain only the NXDL file.
The XML attribute ``units`` gives the units
category or an example of the units, not the value of ``@units``.
Other NeXus attributes of the NeXus field are defined with
NXDL attributes.

Note that an NXDL field also includes the declarations of the
``basicComponent`` complex type.
(The ``fieldType`` complex type is used internally in the NXDL schema
to declare elements and XML attributes to be used in NXDL files.)


XML attribute axes
++++++++++++++++++

    

    NOTE: Use of the XML attribute ``axes`` for an
    NXDL field is discouraged.  It is for legacy
    support. You should use the NeXus attribute
    ``@axes`` of the NeXus group (such as in NXdata) instead.
    
    This XML attribute contains a string array that
    defines the independent NeXus fields used in
    the default plot for all of the dimensions
    of the *signal* field (the *signal* field is
    the NeXus field in this NeXus group that is named by the
    NeXus attribute ``@signal`` of this NeXus group).
    
    When there is only one item in the string array,
    it is acceptable to set the value to the one string.
    In such case, it is not necessary to make it
    an array of one string.
    
    Presence of the XML attribute ``axes`` means
    this NeXus field is an ordinate.
    

XML attribute axis
++++++++++++++++++

    

    NOTE: Use of this XML attribute is discouraged.  It is for legacy support.
    You should use the NeXus group
    attribute ``@axes`` (such as in NXdata) instead.
    
    Presence of the XML attribute ``axis`` means this NeXus field is an abscissa.
    
    The XML attribute value is an integer indicating this
    NeXus field as an axis that is part of the data set.
    The data set is a NeXus field in the same NeXus group whose
    content fields have the content attribute ``@signal=1``.
    The value can range from 1 up to the number of
    independent axes (abscissae) in the data set.
    
    A value of ``axis="1"`` indicates that this NeXus field
    contains the data for the first independent axis.
    For example, the X axis in an XY data set.
    
    A value of ``axis=2`` indicates that this NeXus field
    contains the data for the second independent axis.
    For example, the Y axis in a 2-D data set.
    
    A value of ``axis=3`` indicates that this NeXus field
    contains the data for the third independent axis.
    For example, the Z axis in a 3-D data set.
    
    An NXDL field with an XML attribute ``axis`` should
    not have an XML attribute ``signal``.
    

XML attribute data_offset
+++++++++++++++++++++++++

    

    Deprecated: not used by any NeXus definition; :ref:`NXobject` defines the NeXus
    attribute that describes the content attribute in a data file.  The
    declaration of this XML attribute constrains only the NXDL file: its
    type and default never applied to the content attribute in a data file.
    
    The XML attributes ``stride`` and ``data_offset``
    are used together to index the array of data items in a
    multi-dimensional array.  They may be used as an alternative
    method to address a data array that is not stored in the standard NeXus
    method of "C" order.
    
    The XML attribute ``data_offset``
    determines the starting coordinates of the data array
    for each dimension.
    
    See https://support.hdfgroup.org/HDF5/Tutor/phypereg.html
    or *4. Dataspace Selection Operations* in
    https://portal.hdfgroup.org/display/HDF5/Dataspaces
    
    The XML attribute ``data_offset`` contains a
    comma-separated list of integers.
    (In addition to the required comma delimiter,
    whitespace is also allowed to improve readability.)
    The number of items in the list
    is equal to the rank of the data being stored.  The value of each
    item is the offset in the array of the first data item of that
    subscript of the array.
    

XML attribute interpretation
++++++++++++++++++++++++++++

    

    Deprecated: not used by any NeXus definition; :ref:`NXobject` defines the NeXus
    attribute that describes the content attribute in a data file.  The
    declaration of this XML attribute constrains only the NXDL file: its
    type and default never applied to the content attribute in a data file.
    
    This instructs the consumer of the data what the last dimensions
    of the data are. It allows plotting software to work
    out the natural way of displaying the data.
    
    For example a single-element, energy-resolving, fluorescence detector
    with 512 bins should have ``interpretation="spectrum"``. If the
    detector is scanned over a 512 x 512 spatial grid, the data reported
    will be of dimensions: 512 x 512 x 512.
    In this example, the initial plotting representation should default to
    data of the same dimensions of a 512 x 512 pixel ``image``
    detector where the images where taken at 512 different pressure values.
    
    In simple terms, the allowed values mean:
    
    * ``scalar`` = 0-D data to be plotted
    * ``scaler`` = DEPRECATED, use ``scalar``
    * ``spectrum`` = 1-D data to be plotted
    * ``image`` = 2-D data to be plotted
    * ``rgb-image`` = 3-D data to be plotted
    * ``rgba-image`` = 3-D data to be plotted
    * ``hsl-image`` = 3-D data to be plotted
    * ``hsla-image`` = 3-D data to be plotted
    * ``cmyk-image`` = 3-D data to be plotted
    * ``vertex`` = 3-D data to be plotted
    

XML attribute long_name
+++++++++++++++++++++++

    

    Deprecated: not used by any NeXus definition; :ref:`NXobject` defines the NeXus
    attribute that describes the content attribute in a data file.  The
    declaration of this XML attribute constrains only the NXDL file: its
    type and default never applied to the content attribute in a data file.
    
    Descriptive name for this NeXus field (may include whitespace and engineering units).
    Often, the long_name (when defined) will be used as the axis label on a plot.
    

XML attribute maxOccurs
+++++++++++++++++++++++

    

    Maximum number of content fields, described by the NeXus field that
    this NXDL field defines, in one parent content group.  Its
    value is confined to zero or greater.  Must be greater than or equal to
    the value for the XML attribute ``minOccurs``.
    A value of "unbounded" is allowed.
    

XML attribute minOccurs
+++++++++++++++++++++++

    

    Minimum number of content fields, described by the NeXus field that
    this NXDL field defines, in one parent content group.  Its
    value is confined to zero or greater.  Must be less than or equal to
    the value for the XML attribute ``maxOccurs``.
    

XML attribute optional
++++++++++++++++++++++

    

    A value of "true" is equivalent to minOccurs=0 while a value of
    "false" is equivalent to minOccurs>0.
    

XML attribute primary
+++++++++++++++++++++

    

    Integer indicating the priority of selection
    of this NeXus field for plotting (or visualization) as an axis.
    
    Presence of the XML attribute ``primary`` means this
    NeXus field is an abscissa.
    

XML attribute recommended
+++++++++++++++++++++++++

    

    A synonym for optional, but with the recommendation that the
    content field, described by the NeXus field this NXDL field defines, be present.
    

XML attribute signal
++++++++++++++++++++

    

    Presence of the XML attribute ``signal`` means this NeXus field is an ordinate.
    
    Integer marking this NeXus field as plottable data (ordinates).
    The value indicates the priority of selection or interest.
    Some facilities only use ``signal=1``
    while others use ``signal=2`` to indicate
    plottable data of secondary interest.
    Higher numbers are possible but not common
    and interpretation is not standard.
    
    An NXDL field with an XML attribute ``signal`` should not have an XML attribute ``axis``.
    

XML attribute stride
++++++++++++++++++++

    

    Deprecated: not used by any NeXus definition; :ref:`NXobject` defines the NeXus
    attribute that describes the content attribute in a data file.  The
    declaration of this XML attribute constrains only the NXDL file: its
    type and default never applied to the content attribute in a data file.
    
    The XML attributes ``stride`` and ``data_offset``
    are used together to index the array of data items in a 
    multi-dimensional array.  They may be used as an alternative
    method to address a data array that is not stored in the standard NeXus
    method of "C" order.
    
    The ``stride`` list chooses array locations from the
    data array  with each value in the ``stride`` list
    determining how many elements to move in each dimension.
    Setting a value in the ``stride`` array to 1 moves
    to each element in that dimension of the data array, while
    setting a value of 2 in a location in the ``stride``
    array moves to every other element in that dimension of the
    data array.  A value in the ``stride`` list may be
    positive to move forward or negative to step backward.
    A value of zero will not step (and is of no particular use).
    
    See https://support.hdfgroup.org/HDF5/Tutor/phypereg.html
    or *4. Dataspace Selection Operations* in
    https://portal.hdfgroup.org/display/HDF5/Dataspaces
    
    The XML attribute ``stride`` contains a
    comma-separated list of integers.
    (In addition to the required comma delimiter,
    whitespace is also allowed to improve readability.)
    The number of items in the list
    is equal to the rank of the data being stored.  The value of each
    item is the spacing of the data items in that subscript of the array.
    

XML attribute type
++++++++++++++++++

    

    Defines the type of the NeXus field as allowed by NeXus.
    
    See :ref:`here<Design-DataTypes>` and :ref:`elsewhere<nxdl-types>` for the complete list of allowed types.
    

XML attribute units
+++++++++++++++++++

    

    String describing the engineering units.
    The string should be appropriate for the value.
    
    * If a unit is not provided by the list of NeXus 
      unit categories, instead of providing a category, 
      an NXDL field can include an example of the 
      units directly.
    
    * The example does not constrain the scale of the 
      units. For example, if the unit is ``eV/mm``, the
      user could specify in a data file ``eV/cm``, or any 
      other unit that is convertible to the example given.
    
    It is recommended that users and application developers 
    check if their units and their unit examples adhere to 
    the UDUNITS standard.  [#]_
    
    Conformance is not validated at this time.
    
    .. [#] https://www.unidata.ucar.edu/software/udunits/
    

attribute
+++++++++

    

    NeXus attributes to be used with this NeXus field
    

dimensions
++++++++++

    

    dimensions of the NeXus field
    

enumeration
+++++++++++

    

    An NXDL field can specify which values are to be used

fieldAttributesType
-------------------



An NXDL ``fieldAttributes`` defines NeXus attributes that describe the
content attributes of every content field directly in a content group,
whether or not a NeXus field describes it.  Content fields in nested content groups are not affected.

* As a child of the NXDL definition of a base class, it applies to every
  content field directly in a content group of that class, and is
  inherited by the classes that extend it (see :ref:`NXobject`).
  An application definition has no content groups of its own class, so
  it may not have ``fieldAttributes`` as a direct child (checked by the
  repository's Python syntax check, not by ``nxdl.xsd``).
* As a child of an NXDL group, it applies to every content field directly
  in the content groups described by the NeXus group that this NXDL group
  defines, in addition to the ``fieldAttributes`` of the class of that
  NeXus group.

An NXDL attribute of an NXDL field always takes
precedence over one with the same name in ``fieldAttributes``.
When several ``fieldAttributes`` contain an NXDL attribute with the
same name, the one closest to the NXDL field takes precedence: the
enclosing NXDL group, then the same NXDL group in the application
definitions that its NXDL definition extends (closest first), then the
NXDL definition of the type of its NeXus group, then the classes that
class extends.
The NXDL attribute that takes precedence replaces the others, as a
subclass overrides an inherited NeXus item (see :ref:`inheritance`).
Could contain these elements:

* ``attribute``
* ``doc``

(This complex type is used internally in the NXDL schema
to declare elements and XML attributes to be used in NXDL files.)


Elements of fieldAttributesType
+++++++++++++++++++++++++++++++

attribute
+++++++++

    

    A NeXus attribute that describes a content attribute of every content field directly in the content groups that ``fieldAttributes`` applies to.
    

doc
+++

    

    Describe these NeXus attributes.
    This documentation will go into the manual.

.. _NXDL.data.type.linkType:

linkType
--------



An NXDL link defines a :ref:`NeXus link <Design-Links>`: a NeXus item
that names another NeXus field or group, its target.  It describes a content
field or group with the same shared content as one that its target describes;
one of the two is a content link to the other, or both are content links to
the same target.
Use it to avoid needless repetition of information.

In a data file this requires that

* the content group described by the enclosing NeXus group contains a content
  field or group whose name is the value of the XML attribute ``name``;
* it and a content field or group that the target describes have the same shared content;
* one of the two is a content link to the other, or both are content links
  to the same target: the content attribute ``@target`` (see :ref:`NXobject`)
  of one is the path of the other, or both have the same ``@target``.

Either of the two may be the content link.

An NXDL link defines no type, units, dimensions or NeXus attributes
of its own: those of its target apply.
An NXDL link has no occurrence XML attributes, so it is required
in an application definition.

A content field or group may be a content link in a data file without a
NeXus link describing it.
(This complex type is used internally in the NXDL schema
to declare elements and XML attributes to be used in NXDL files.)


XML attribute napimount
+++++++++++++++++++++++

    

    Deprecated: not used by any NeXus definition.
    URL of an HDF5 group in another file
    (see :ref:`design.external_file_link`).
    NXDL enforces nothing about it.
    

XML attribute target
++++++++++++++++++++

    

    Class path of the target: the NeXus field or group whose content
    fields or groups must have the same shared content
    (see :ref:`NXDL.data.type.validTargetName`).  It is written with
    class names, so it names a NeXus item, not a path in a data file.
    
    NXDL does not require that the value of the content attribute ``@target`` matches this path.
    
    This XML attribute is not the content attribute ``@target`` of a
    content field or group in a data file (see :ref:`NXobject`).
    
    For example, an NXDL group of type ``NXdata`` that contains::
    
    	<link name="polar_angle" target="/NXentry/NXinstrument/NXdetector/polar_angle"/>
    
    is satisfied by this data, where both content fields have the same shared content::
    
    	entry:NXentry
    		data:NXdata
    			polar_angle:NX_NUMBER
    				@target="/entry/instrument/detector/polar_angle"
    		instrument:NXinstrument
    			detector:NXdetector
    				polar_angle:NX_NUMBER
    					@target="/entry/instrument/detector/polar_angle"

validItemName

    [a-zA-Z0-9_]([a-zA-Z0-9_.]*[a-zA-Z0-9_])?

.. index:: ! validTargetName (NXDL data type)


.. _NXDL.data.type.validTargetName:

validTargetName
---------------



An absolute :ref:`class path <preface.Class.path.specification>` naming a
NeXus field or group, used as the XML attribute ``target`` of an NXDL link.
Each ``/``-separated segment is the class of a NeXus group (``NXcrystal``),
the name and class of a NeXus group (``analyzer:NXcrystal``), or the name of
a NeXus field (``ef``)::

	/NXentry/NXinstrument/analyzer:NXcrystal/ef
	/NXentry/NXinstrument/monochromator:NXcrystal/ei
	/NX_other

Because it is written with class names, it names a NeXus item,
not a path in a data file.
Currently it must be an absolute path; we may want to consider
allowing "``..``" (parent of directory) at some point.
Must also consider use of the XML attribute ``name`` in resolving NXDL link targets.
(This data type is used internally in the NXDL schema 
to define a data type.)




From the HDF5 documentation:

	*Note that relative path names in HDF5 do not employ the ``../`` notation, 
	the UNIX notation indicating a parent directory, to indicate a parent group.*

Thus, if we only consider the case of 
``[name:]type``, the matching regular expression syntax
is written: ``/[a-zA-Z_][\w_]*(:[a-zA-Z_][\w_]*)?)+``.
Note that HDF5 also permits relative path names, such as:
``GroupA/GroupB/Dataset1``
but this is not permitted in the matching regular expression.


The value may be any
``xs:token`` that *also* matches the regular expression::

    (/[a-zA-Z_][\w_]*(:[a-zA-Z_][\w_]*)?)+

    The ``xs:string`` data type can contain characters,
    line feeds, carriage returns, and tab characters.
    See https://www.w3schools.com/xml/schema_dtypes_string.asp
    for more details.

**The** ``xs:token`` **data type**
    The ``xs:string`` data type is derived from the
    ``xs:string`` data type.

    The ``xs:token`` data type also contains characters,
    but the XML processor will remove line feeds, carriage returns, tabs,
    leading and trailing spaces, and multiple spaces.
    See https://www.w3schools.com/xml/schema_dtypes_string.asp
    for more details.
